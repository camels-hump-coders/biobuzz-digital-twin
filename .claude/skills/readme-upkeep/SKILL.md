# Keep the README, the team skill and the screenshots current

This repo's README is the product manual for mentors, students and agents, and `skills/biobuzz-twin/SKILL.md`
is what a team's coding agent reads. Both drift the moment a feature lands without a sentence. Do this at the end
of any change a user could notice; it takes minutes.

## 1. README.md — every user-visible change gets words

Find the section that owns the change and update it in place (do not append a changelog):

| Change | Section |
|---|---|
| panel control, shortcut, HUD row, overlay | *Run the twin*, *Controls*, *Mat overlays*, *What the HUD tells you* |
| `pnpm sim` / `pnpm twin-test` flag, host behaviour, Panels | *Run your TeamCode against the twin*, *Test bed for coding agents* |
| agent API endpoint | *Agent API* (add the curl line) and the host's `AgentApi.help()` |
| timeline, replay, logs | *Timeline & logs* |
| asset settings, schema, bindings, export/save | *TeamCode settings*, *Twin bindings* |
| match rules, scoring, start positions | *Match flow* |
| settings file, session, reset | *Saving, sharing and resetting* |
| launcher, calibration | *Launcher model* |
| modelling shortcut or known gap | *Known simplifications* |

Rules: one paragraph per idea, say what the user does and what they see, name the exact button or flag, keep
numbers out of prose unless they change a decision. Remove sentences the change made false (grep the README for
the old button name or behaviour). Keep the feature list at the top of the README in step: it is the one place a
new reader learns what exists.

## 2. The team-facing skill (`skills/biobuzz-twin/SKILL.md`)

If the change touches how an agent runs scenarios, reads results, edits settings, keeps bindings or schemas, or
uses the agent API, update the matching numbered section there too, with the exact command. That file is copied
into team repos by `npx skills add` / `pnpm skill:install`, so a stale instruction misleads every team.

## 3. Screenshots (`docs/screenshots/`, regenerated by `pnpm gallery`) — only on major visual change

Refresh the gallery when the panel layout, a HUD block, a dialog or a visual feature that appears in a screenshot
changed, or when a new visual capability deserves a tile. Do not refresh for copy edits, colour tweaks or
non-visual work; each full refresh rewrites the gallery PNGs.

```bash
pnpm sim --built --wip --no-browser --no-panels --port 5180 --host-port 8780 --team <team repo>   # terminal 1 (server mode gives the runtime, editor, replay and calibration shots)
pnpm gallery -- --port 5180 --host-port 8780                                   # terminal 2; --only overview,top-view redoes a subset
```

For isolated captures, run `pnpm dev -- --port 5180` and `pnpm gallery -- --port 5180 --demo-runtime`; label the runtime and calibration examples in the gallery captions. `--wip` above is required when documenting uncommitted UI changes because plain `--built` serves HEAD.

Then look at every new PNG (Read tool) before committing: a shot with an empty panel, a missing dialog or a robot
in a wall is worse than the old one. Update the gallery table captions in the README if a tile's content changed,
and add a row for a new tile. `scripts/gallery.mjs` is the only way screenshots are made; if a shot needs a new
setup, change the script, not the process.

## 4. Before committing

- `pnpm typecheck && pnpm test`; a headless run of the affected path (`pnpm twin-test …`, or a Playwright script
  against the built twin) for anything the tests do not cover.
- `LICENSE` is MIT; third-party notices (AprilRobotics tag codes, goBILDA CAD, FTC Panels) stay listed in the
  README's *License* section when new third-party material comes in.
- The commit message says what changed for the user, then how; attribution lines as the session requires.
